# Перф-бейзлайн каталога (задача 31)

Разовая ручная проверка p95 листинга каталога (`GET /api/v1/institutions`) с включённым
Redis-кэшем (`CachedService`, TTL 60с, singleflight). Не постоянный мониторинг — см.
`.claude/rules/devops.md` (Prometheus/Grafana осознанно вне MVP, NFR проверяется вручную
по вехам).

## Окружение

- Дата: 2026-08-30
- Локальный Docker-compose стек этого репозитория: `eduhub-db-1` (Postgres+PostGIS, порт
  хоста 5433), `eduhub-redis-1` (Redis, порт хоста 6380)
- БД засеяна через `cmd/devseed` (`make seed`, `APP_ENV=dev`) — 9 демо-институций
- `cmd/api` запущен локально (`go run ./cmd/api`), не в контейнере — не production-нагрузка,
  ориентир для дальнейших вех, не гарантия прод-производительности под реальным трафиком
- Машина разработчика (macOS), не выделенный бенчмарк-стенд — абсолютные числа не
  переносимы 1:1 на прод-инфраструктуру, важен факт «кэш даёт кратный выигрыш и укладывается
  в NFR с большим запасом»

## Команда

```
go run github.com/rakyll/hey@latest -z 20s -c 50 'http://localhost:8090/api/v1/institutions?region=dushanbe'
```

на каждый запрос.

p95 без кэша — 7.9мс, тоже с запасом укладывается в NFR (локальная БД с 9 строками — заведомо

## Вывод

Критерий приёмки задачи 31 выполнен: `p95 < 300мс` — с более чем стократным запасом в обоих
режимах на текущем объёме данных. Число появится осмысленным ориентиром только на следующих
вехах, при реальном объёме институций и наличии `catalog:version`-инвалидации (веха 3).
