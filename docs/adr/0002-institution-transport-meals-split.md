# ADR-0002: Транспорт и питание учреждения — 1:N сателлитные таблицы, не колонки

## Статус
Принято

## Дата
2026-08-28

## Контекст
Изначальный дизайн (веха 1, задача 17, миграция `00002_catalog_institutions.sql`) хранил транспорт и питание как плоские колонки на `catalog.institutions`: `transport_type/cost/areas`, `meals_available/type/cost/halal`. Решение было обосновано скоуп-правилом MVP (существовало в `CLAUDE.md` на момент проектирования, позже удалено оттуда отдельным решением): если учреждение заполняет поле один раз при регистрации — это информационное поле, входит в MVP как есть, без операционной надстройки. Транспорт/питание считались именно такими — одна запись на учреждение.

Консультация с go-advisor на этом этапе подтвердила плоский дизайн, явно на основании подтверждённой 1:1-кардинальности: группы заполняются один раз, тот же владелец, та же частота записи, что и у корневой таблицы — ни один критерий для выноса в сателлит не выполнялся. При этом вердикт прямо называл условие, при котором вывод стал бы противоположным: если группа получит 1:N-кардинальность.

Продуктовое требование пересмотрено: учреждение может иметь **несколько независимых маршрутов транспорта** (каждый со своей ценой, типом транспорта, районом охвата) и **несколько вариантов питания** (каждый со своей ценой) — как самостоятельные записи, не поля-сводка одной строки. Это ровно тот триггер, который был назван условием пересмотра.

Момент правки — до коммита задачи 17, ни Go-код, ни данные ещё не существуют, значит цена реверса нулевая: нет бэкфилла, нет рефакторинга use case/repo-слоя.

## Рассмотренные варианты

### Вариант A: Оставить плоские колонки на `catalog.institutions`
- **Плюсы**: не требует новых таблиц, один SQL на чтение и запись карточки.
- **Минусы**: физически не может выразить несколько маршрутов/планов питания — данные, которые продукт теперь требует хранить, некуда положить без искажения (например конкатенация в одну строку).
- **Риски**: любое обходное решение поверх плоской схемы (см. варианты B/C) хуже прямого сателлита.

### Вариант B: JSONB-массив в одной колонке (`transport_routes JSONB`)
- **Плюсы**: одна колонка на группу, не нужна отдельная миграция для новой таблицы.
- **Минусы**: нет CHECK/enum-валидации отдельных элементов массива на уровне БД; любое изменение одного маршрута требует read-modify-write всего массива (гонки при параллельном редактировании из кабинета учреждения); фильтрация/агрегация по содержимому JSONB заметно дороже типизированных колонок.
- **Риски**: тихая деградация качества данных — ничто не мешает записать в массив произвольную структуру.

### Вариант C: Пронумерованные колонки (`transport_type_1`, `transport_type_2`, `transport_type_3`, …)
- **Плюсы**: остаётся в рамках одной таблицы.
- **Минусы**: классический анти-паттерн повторяющихся групп — жёсткий искусственный потолок на число маршрутов, NULL-колонки для неиспользуемых слотов, кошмарные запросы для агрегации/фильтрации по «любому из N».
- **Риски**: при росте потребности (учреждение с 5+ маршрутами) схема требует очередной миграции добавления колонок.

### Вариант D (выбран): Сателлитные таблицы `institution_transport_routes` / `institution_meal_plans`
Зеркалирование уже существующего в проекте паттерна `catalog.institution_gallery` (1:N, `institution_id` FK ON DELETE CASCADE, `sort_order` для порядка отображения, без собственного `updated_at` — версия всей карточки берётся от родителя).
- **Плюсы**: естественно выражает 1:N; CHECK-валидация типа/периода цены на уровне БД для каждой записи отдельно; фильтры листинга (`?transport=true/false`, `?food=true/false`) реализуются как `EXISTS`/`NOT EXISTS` подзапрос по индексированному `institution_id` — не портит план сортировки по частичному индексу `(rating_avg DESC, id) WHERE moderation_status='approved'`, в отличие от JOIN; «нет транспорта» выражается нулём строк, без специального значения-заглушки типа `'none'`.
- **Минусы**: два дополнительных `LEFT JOIN LATERAL` в запросе карточки (задача 24) — держит инвариант «один SQL-запрос на карточку», но требует явного `ORDER BY sort_order, created_at, id` внутри каждого `json_agg`, иначе порядок элементов не детерминирован между вызовами и ETag (задача 28) может отдать `304` на фактически изменившееся содержимое; мутация сателлита обязана поднимать `institutions.updated_at` в той же транзакции — явный инвариант write-path (веха 3, E3.4), не обеспечивается автоматически.
- **Риски**: без верхнего предела числа строк на учреждение — вектор злоупотребления (сотни «маршрутов» ради визуального объёма карточки); закрывается guard-проверкой в usecase (не в БД), не входит в задачу 17/19, но зафиксировано как открытый пункт для вехи 3.

Повторная консультация с go-advisor по конкретному дизайну варианта D дала 6 правок к первой версии: `label {ru,tg}` также на `institution_meal_plans` (не только на маршрутах — иначе два варианта питания с одинаковым `meal_type` и разной ценой неразличимы); `cost_period` (`month`/`day`/`trip`) — без периода число цены неоднозначно; `halal` — nullable, а не `NOT NULL DEFAULT false` (в контексте Таджикистана «не халяль» и «не указано» — разные факты); `areas` — bilingual JSONB `{ru,tg}[]` по существующей конвенции проекта, не код района (в проекте нет справочника районов — `institutions.district` сам свободный текст, вводить новый справочник ради этой правки было бы расширением скоупа); `'other'` добавлен в оба enum (`type`/`meal_type`), поскольку контракт фильтрации сегодня булев (`?transport=`/`?food=`), не по конкретному типу — список значений не должен становиться источником отказа записи.

## Решение
Выбран вариант D, потому что:
1. Это единственный вариант, который физически и без искажений выражает подтверждённое продуктовое требование (несколько независимых маршрутов/планов питания, каждый со своей ценой) — варианты A/B/C либо не могут хранить эти данные корректно, либо жертвуют валидацией/масштабируемостью ради экономии одной миграции.
2. Момент реверса минимизирует его стоимость: задача 17 ещё не закоммичена, нет ни строки Go-кода, ни единой строки данных — правка стоит ровно столько, сколько правка двух ещё не выпущенных миграций и трёх абзацев документации, а не бэкфилл-эпопея на будущее.
3. Дизайн зеркалирует уже принятый в проекте паттерн (`catalog.institution_gallery`) — не вводит новую архитектурную идиому, только применяет существующую там, где теперь есть настоящая 1:N-потребность.

## Последствия
- **Положительные**: карточка учреждения может корректно отображать произвольное число маршрутов транспорта и вариантов питания с индивидуальными ценами; фильтры `?transport`/`?food` остаются дешёвыми (`EXISTS` по индексу) без денормализации и триггеров; «нет транспорта/питания» больше не нуждается в значении-заглушке в CHECK-списке.
- **Отрицательные**: сборка карточки учреждения (задача 24) усложняется двумя дополнительными `LEFT JOIN LATERAL`; появляется явный write-path инвариант (bump `institutions.updated_at` при мутации любого сателлита), который ничем не принуждается автоматически, кроме дисциплины в usecase-слое вехи 3.
- **Технический долг, принимаемый осознанно**: верхний предел числа строк на учреждение (маршруты/планы питания) не в БД, а в usecase — потенциальный пробел до вехи 3, когда появятся мутирующие эндпоинты; денормализация фильтров `transport`/`food` в булевы колонки на `institutions` намеренно отложена — решение обратимо (невидимо в API-контракте), пересмотреть при реальном обосновании нагрузкой на масштабах, для которых `EXISTS`-подзапрос перестанет быть дешёвым (ориентир — сотни тысяч+ институций, далеко за пределами MVP для Таджикистана).
