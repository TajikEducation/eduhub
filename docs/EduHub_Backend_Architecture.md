# EduHub — архитектура бэкенда

**Статус:** согласовано, справочный документ

Этот документ — единая точка входа в архитектурные решения бэкенда: структура кода, границы сервисов, сквозные паттерны (логирование, ошибки, конкурентность, кэширование, безопасность). Детальный план реализации по вехам — `docs/EduHub_Backend_Development_Plan.md`. Полная схема БД — `docs/EduHub_Database_Schema.md`. Состав тарифов — `docs/EduHub_Pricing_Tiers.md`. Функциональные требования — `docs/EduHub_Functional_Requirements.md`.

---

## 1. Архитектурный стиль

**Модульный монолит с внутренними SOA-границами.** Один Go-бинарник (`cmd/api`), развёрнутый как один процесс/контейнер — не микросервисная сетка. Внутри — шесть логически изолированных сервисов (`auth`, `catalog`, `reviews`, `communications`, `analytics`, `moderation`), каждый со своим доменом, слоем use case, репозиторием и HTTP-транспортом, но исполняющихся в одном процессе и общающихся через Go-интерфейсы, не по сети.

**Почему не микросервисы.** Один разработчик, нет отдельных команд с разными циклами релиза. Настоящие микросервисы окупаются, когда нужна независимая деплой-каданс, разное масштабирование под нагрузку разных доменов, изоляция отказа одного сервиса от других. При одном разработчике всё это — чистые накладные расходы: N контейнеров, N конфигов, сетевая задержка между сервисами (прямой удар по NFR p95≤300мс на каждый лишний HTTP-хоп), сложность деплоя, рассинхрон версий зависимостей.

**Почему это не тупик.** Если продукт вырастет и понадобится реальное разделение — оно будет **механическим**, потому что границы уже проведены как для распределённой системы: без прямых импортов между сервис-пакетами, база разбита на схемы по владению. Тогда `internal/communications`, например, просто выносится в отдельный бинарник, а Go-интерфейсы заменяются на HTTP/gRPC-клиенты — без переписывания бизнес-логики.

## 2. Раскладка каталогов

```
backend/
  cmd/
    api/            — точка входа, сборка зависимостей, graceful shutdown
    devseed/        — сидер демо-данных из web/lib/data.ts (только APP_ENV=dev)
    worker/         — фоновые задачи (появляется с вехи 4: пересчёт рейтинга,
                       управление партициями, ночная агрегация аналитики)
  migrations/       — goose-миграции, сквозная нумерация по всем схемам
  internal/
    platform/       — общая инфраструктура, не знает про домены
      config/       — загрузка и валидация конфигурации из ENV
      logger/       — обёртка над slog
      pg/           — пул соединений pgx
      redis/        — клиент Redis
      httpx/        — роутер, middleware-цепочка, JSON in/out, маппинг ошибок
      apperr/        — таксономия доменных ошибок
      idempotency/  — идемпотентность мутирующих запросов по ключу
      clock/        — инжектируемое время (для тестов без time.Sleep)
    moderation/     — сквозной пакет: audit trail + очередь модерации,
                       используется всеми остальными сервисами через порт
    auth/           — аккаунты, сессии, RBAC, привязка ребёнка/трудоустройства
      domain/ usecase/ repo/postgres/ transport/http/
    catalog/        — учреждения, поиск, фильтры, сравнение
      domain/ usecase/ repo/postgres/ transport/http/
    reviews/        — отзывы, рейтинг, отзывы о работодателе
      domain/ usecase/ repo/postgres/ transport/http/
    communications/ — чат, уведомления, вакансии, отклики
      domain/ usecase/ repo/postgres/ transport/http/
    analytics/      — события просмотров/кликов, агрегация, дашборд
      domain/ usecase/ repo/postgres/ transport/http/
```

Файл `backend/CLAUDE.md`/`AGENTS.md` не заводится отдельно — правила читаются из корневого `CLAUDE.md` и `.claude/rules/*` репозитория, они уже покрывают Go-специфику (`go.md`), БД (`db.md`, `migrations.md`), архитектуру (`architecture.md`), безопасность (`security.md`).

## 3. Слои и правило зависимостей (Clean Architecture)

Внутри каждого сервис-пакета — четыре слоя, зависимости направлены строго внутрь:

```
transport/http  →  usecase  →  domain
                       ↑
                  repo/postgres
```

- **`domain`** — чистые доменные сущности и инварианты модели. Не импортирует `net/http`, не импортирует `pgx` или любой драйвер БД. Проверяется механически: `go list -deps ./internal/<service>/domain | grep -E 'net/http|pgx'` должен быть пустым — это архитектурный тест, не пожелание.
- **`usecase`** — оркестрация, бизнес-инварианты операции, authz-guard, идемпотентность. Зависит от `domain` и от интерфейсов, которые сам объявляет (порты) — не от конкретной реализации `repo`.
- **`repo/postgres`** — реализует интерфейс, объявленный в `usecase`. Никакой бизнес-валидации — только техническая корректность (маппинг `NULL→*T`, `pgx.ErrNoRows→apperr.NotFound`).
- **`transport/http`** — HTTP DTO, парсинг/нормализация запроса, маппинг domain→response. Не отдаёт доменные структуры напрямую наружу — только через явный DTO-слой (иначе любое поле домена случайно утекает в публичный контракт).

**Запрет прямого импорта между сервис-пакетами.** `internal/catalog` не может импортировать `internal/reviews` напрямую. Если catalog нуждается в чём-то из reviews — объявляется интерфейс-порт на стороне потребителя (`catalog`), и `reviews` (или его конкретная реализация, связанная в `cmd/api`) реализует этот интерфейс. Это единственный способ, которым сервис-пакеты «видят» друг друга.

### Размещение валидации — сквозное правило

| Слой | Что проверяет | Пример |
|---|---|---|
| Transport (HTTP DTO / middleware) | Синтаксис: required/format/enum/диапазон, парсинг query, нормализация | `sort ∈ {score,price_asc,...}`; `lat ∈ [-90,90]` |
| Usecase | Семантика: инварианты операции, orchestration, authz, идемпотентность | `min_price ≤ max_price`; публично видны только `moderation_status='approved'` |
| Domain | Чистые инварианты модели, без transport/DB | `Rating.Score ∈ [1,5]`; `Filter.Normalize()` |
| Repo | Никакой бизнес-валидации, только техническая корректность | маппинг NULL, коды ошибок Postgres |

Правило разделения: если проверку можно сделать не зная состояния системы — она в transport; если нужны другие поля/БД/политика — она в usecase. Дублирование запрещено.

## 4. Границы сервисов и владение схемами БД

Одна PostgreSQL+PostGIS база `eduhub`, разбитая на 7 схем по владению: `auth`, `catalog`, `reviews`, `moderation`, `communications`, `analytics`, `platform`. **Пишет в схему только сервис-владелец.** Кросс-схемные внешние ключи запрещены, кроме двух явно согласованных исключений (`auth.children.institution_id`, `auth.employment_claims.institution_id` — оба ссылаются на `catalog.institutions`, обоснование — в `docs/EduHub_Database_Schema.md`). Всё остальное межсервисное взаимодействие — по значению (хранить `user_id`/`institution_id` как значение без FK) или через порт-интерфейс, проверяющий существование/статус в usecase-слое.

Это правило — прямое следствие модульного монолита: если бы одна схема свободно ссылалась на другую через FK и читала её таблицы напрямую, граница между «сервисами» была бы фиктивной, и при будущем разделении на настоящие микросервисы БД пришлось бы физически резать по живому.

## 5. Взаимодействие между сервисами

**Внутри процесса (сейчас) — Go-интерфейсы**, объявленные потребителем, реализация связывается в `cmd/api/main.go`. Ноль сетевых хопов, бюджет p95 не страдает.

**Асинхронно, между сервисами с разной скоростью изменения состояния** — паттерн **transactional outbox + Redis Streams**:
1. Публикующая транзакция (например, публикация отзыва) пишет и доменные данные, и запись в собственную `outbox`-таблицу схемы-источника — одной транзакцией.
2. Отдельный релей-воркер (`cmd/worker`) вычитывает неотправленные `outbox`-записи (`FOR UPDATE SKIP LOCKED`, батчами) и публикует их в Redis Stream.
3. Консьюмер на стороне потребителя (например, `catalog`, синхронизирующий агрегат рейтинга) обрабатывает событие.

**Идемпотентность консьюмера — по факту операции, не универсальным способом.** Redis Streams даёт at-least-once доставку — повтор гарантирован, не «может случиться». Если операция естественно идемпотентна (пишет абсолютное значение, не инкремент — как `RatingSync.Apply`, пересчитывающий текущее взвешенное среднее) — отдельный dedup-стор не нужен. Если не идемпотентна по построению (отправка push-уведомления — повторная доставка реально отправит второй push) — нужна таблица обработанных `event_id` (`communications.processed_events`), консьюмер вставляет `event_id` перед обработкой, конфликт вставки = «уже обработано».

**Синхронный HTTP между сервисами** — не используется вообще, пока всё в одном процессе. Появится только при физическом разделении в будущем, и то — максимум один хоп на запрос (бюджет 300мс не терпит цепочек).

## 6. Конфигурация

`internal/platform/config` — единственная точка чтения переменных окружения (`os.Getenv`, без сторонних библиотек — оправдано для нескольких десятков полей, порог пересмотра в пользу struct-tag библиотеки типа `caarlos0/env` — свыше ~15 полей или появление вложенных секций конфигурации, не раньше). `Load() (Config, error)` — fail-fast: валидирует все поля разом (не первое найденное), возвращает агрегированную ошибку со списком всех проблем, чтобы разработчик не чинил конфиг по одной ошибке за перезапуск. Каждое поле, критичное для последующего поведения (`AppEnv`, `LogLevel`), — закрытый enum с дефолтом, не свободная строка. Секреты (`DATABASE_URL` с паролем) реализуют `slog.LogValuer` — при случайном логировании конфига целиком пароль маскируется автоматически, не полагаясь на дисциплину вызывающего кода.

Пакет `config` не логирует, не зависит от `net/http`/`pgx` — чистый платформенный строительный блок, доступный любому слою.

## 7. Логирование

`slog`, структурированный JSON. `request_id` — обязательное поле каждой записи, генерируется в middleware (задача 6 вехи 0), прокидывается через `context.Context`. **Запрет на PII в логах**: телефоны, email, адреса, полная поисковая строка (`q`-параметр) никогда не попадают в лог-запись — это применяется на уровне access-log middleware (не логирует query-строку целиком) и на уровне доменных типов (`slog.LogValuer` с редактированием, как в `config.Config`).

`logx.PtrOrNil[T](*T) any` — единственный разрешённый способ положить значение опционального поля (`*T`) в лог-запись: возвращает `nil` для nil-указателя вместо паники или разыменования непроверенного указателя.

## 8. Обработка ошибок

Единая таксономия `internal/platform/apperr`: `NotFound`, `InvalidInput`, `Unauthorized`, `Forbidden`, `Conflict`, `RateLimited`, `Internal`. Оборачивание контекстом через `fmt.Errorf("...: %w", err)`, сравнение — через `errors.Is`/`errors.As`, не строковое сравнение текста ошибки. Маппинг в HTTP-код — ровно в одном месте кодовой базы (`httpx.WriteError`), тело ответа стабильного формата:

```json
{"error":{"code":"invalid_input","message":"...","fields":{"min_price":"..."}},"request_id":"..."}
```

Доменные пакеты (`usecase`, `domain`) не знают про HTTP-коды вообще — они возвращают `apperr`-типизированные ошибки, транспортный слой сам решает, в какой HTTP-статус их превратить.

## 9. Конкурентность

**Правило по умолчанию — без параллелизма**, пока нет доказанной необходимости. Карточка учреждения (веха 1) собирается одним SQL-запросом с `LATERAL json_agg`, не через `errgroup` на 4-5 параллельных запросов к БД — параллельные запросы держат несколько соединений пула на один HTTP-запрос одновременно, что душит конкурентность пула при небольшом размере (25 соединений) сильнее, чем экономит время.

**`errgroup.WithContext`+`SetLimit(N)`** — только там, где I/O действительно разнородный (БД + Redis + S3 + внешний провайдер одновременно) — вехи 4-6 (outbox-релей, batch-writer аналитики).

**Долгоживущие компоненты (WebSocket-хаб)** — ровно 2 горутины на соединение (reader/writer), обе завершаются по общему `context.CancelFunc`, `SetReadDeadline`+ping/pong. Запрет «голых» `go func()` без владельца и точки останова. Все тесты параллельных компонентов — обязательно под `-race`, для долгоживущих компонентов (WS-хаб) — soak-тест от 30 минут под нагрузкой с наблюдением за `NumGoroutine()`/памятью, не только короткий тест на утечку.

## 10. Кэширование

Redis — кэш горячих комбинаций фильтров каталога (`catalog:list:v{version}:{hash}`, TTL 60с) с версионированием (запись инкрементирует `catalog:version`, инвалидируя весь список без ожидания TTL) и singleflight против cache stampede при параллельных промахах. **Redis не точка отказа**: короткие таймауты на все обращения, деградация к прямому чтению БД при недоступности кэша (fail-open с логированием, не fail-closed падением запроса).

## 11. Безопасность и AuthZ/AuthN

Пароли — argon2id (PHC-строка хранения, параметры можно поднять без слома старых хешей). JWT access (15 мин) + refresh (30 дней, хранится только хеш) с reuse-detection — предъявление уже использованного refresh отзывает всю ротационную цепочку (`family_id`) и пишет запись в audit. RBAC — middleware `RequireAuth`/`RequireRole`, аксессор контекста всегда возвращает `(Principal, bool)`, никогда голый указатель. Rate-limiting — token bucket (веха 0, per-instance) с явной таблицей покрытия по эндпоинтам (логин, отправка кода подтверждения, чат, загрузка медиа, создание отзыва, обращение к соискателю) — не только там, где «очевидно нужно», а по явному списку в плане реализации.

Аутентификация — email+пароль и Google OAuth как основные равноправные каналы, телефон опционален (SMS-верификация вне MVP-скоупа — платный провайдер, не оправдан на холодном старте).

## 12. Наблюдаемость

**Сознательно вне MVP-скоупа.** Prometheus/Grafana/RED-метрики не внедряются, пока нет стейджинга/прода с реальным трафиком — метрики без скрейпера и дашборда — мёртвая инфраструктура с ненулевой ценой (мидлварь на каждый запрос, решения о cardinality лейблов). NFR (p95≤300мс) на вехах 0-5 проверяется вручную — нагрузочный прогон (`hey` + синтетические данные) как часть критерия готовности конкретной вехи, не постоянный мониторинг. Возврат к этому решению — по факту появления реального деплоя с трафиком, не раньше.

---

## 13. Деплой

Docker, multi-stage build: builder-слой `golang:1.23+` собирает статический бинарник (`CGO_ENABLED=0`), финальный слой — `distroless/static` (без шелла и пакетного менеджера — минимальная поверхность атаки). Секреты — только через переменные окружения контейнера, никогда не запекаются в образ. `docker-compose.yml` — только для локальной разработки (Postgres+PostGIS, Redis, MinIO как S3-совместимая замена; в проде — реальный S3-совместимый провайдер по конфигу). Kubernetes — сознательно вне MVP (Docker для MVP, K8s по мере роста нагрузки, см. `CLAUDE.md`).

---

## 14. Версионирование API

`/api/v1` — единственная версия на MVP. Breaking change до первого продакшн-релиза — правится напрямую (нет внешних потребителей кроме собственного фронтенда в разработке). После релиза — приоритет additive-изменениям (новое опциональное поле, не трогая старое); если breaking неизбежен — версионируется конкретный ресурс, не весь API, с `Deprecation`/`Sunset` HTTP-заголовками и минимум 30 днями параллельной жизни старой версии.

## 15. Тестовая стратегия

TDD-мандат: NO PRODUCTION CODE WITHOUT FAILING TEST FIRST. Цикл RED (тест падает по правильной причине — обязательно зафиксировать, не пропускать) → GREEN (минимальный код) → REFACTOR. Исключение — bootstrap-артефакты без логики (`go.mod`, `Makefile`, `.gitignore`, SQL-миграции): их «тест» — `go build`/`goose up && goose down`, не unit-тест.

Юнит-тесты — на фейковых зависимостях (интерфейсы usecase-слоя), без БД. Интеграционные тесты (`-tags=integration`) — на реальном Postgres (testcontainers или локальный docker-compose), помечены build-тегом, пропускаются (`t.Skip`), если тестовая БД недоступна — не падают. Перф-тесты — точечно на веху, где риск реальный: каталог (веха 1, синтетические 5-10 тыс. институций), ночной пересчёт рейтинга (веха 4, 10-50 тыс. отзывов), WS-хаб (веха 5, soak-тест), batch-writer аналитики (веха 6, влияние на p95 каталога). Миграции проверяются не только на пустой схеме, но и `migrate-up→seed→migrate-down→migrate-up` на заполненной — ловит миграции, валидные на пустой БД, но потенциально ломающиеся на заполненной.

## 16. Соглашение о комментариях

Комментарии в коде (doc-комментарии пакетов/функций/типов, инлайн-комментарии) — на русском языке. Идентификаторы (имена функций/типов/полей/пакетов) — на английском, как в любом идиоматичном Go-коде. Это применяется одинаково к `.go`-файлам, `docker-compose.yml`, SQL-миграциям, `Makefile`, `.env.example`.
