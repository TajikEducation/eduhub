## Модуль 1. Каталог и поиск

### FR-01 / FR-02 / FR-03: Поиск, фасетные фильтры, геопоиск «рядом со мной»

**Цель:**
Родитель открывает платформу и за один экран должен найти релевантные учреждения — по названию, по фильтрам (район, тип, программа обучения, ступень, цена, рейтинг, развозка, питание, скидки) или по расстоянию от своего текущего местоположения. Результат должен обновляться мгновенно при смене любого фильтра, без перезагрузки страницы.

**Что нужно реализовать:**
- **Индекс поиска:** полнотекстовый индекс по названию учреждения (оба языка — ru/tg) + району/области. На старте — `tsvector`-индекс средствами PostgreSQL (`GIN`), более тяжёлый поисковый движок подключается только при росте объёма данных сверх того, что тянет обычный полнотекстовый поиск в базе.
- **Фасетные фильтры как SQL-предикаты:** тип учреждения, регион, диапазон цены, программа обучения (пересечение массивов для мульти-программы), ступень, наличие скидок, минимальный рейтинг. Каждый активный фильтр — дополнительное условие, комбинируются логическим «И».
- **Композитные индексы** под частые комбинации фильтров: регион+тип, регион+цена, сортировка по рейтингу — без индекса под каждую популярную комбинацию фильтрация по большому числу учреждений начнёт заметно замедляться.
- **Геопоиск:** поиск ближайших точек по географическому индексу, сортировка по расстоянию через оператор ближайшего соседа — не построчный расчёт расстояния для каждой записи.
- **Деградация геолокации:** если браузер не даёт GPS — переход на последний выбранный регион пользователя; если и региона нет — сортировка по топ-рейтингу без гео-компонента. Координаты должны приниматься как опциональный параметр, не обязательный.
- **Фильтры отражаются в адресе страницы**, чтобы результат поиска можно было сохранить или переслать ссылкой.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации):
Родитель включает фильтры «Школа» + «до определённой цены» + «есть развозка», не даёт доступ к GPS. Платформа определяет регион по последнему выбору пользователя, применяет фильтры, сортирует по рейтингу (гео недоступно) и отдаёт совпадения одним запросом с использованием подходящего индекса.

**Реализация в коде:**
Единый эндпоинт каталога с опциональными query-параметрами под каждый фильтр. Backend строит запрос через query-builder с явным списком разрешённых полей фильтрации — никакой конкатенации строк, только параметризация. Кэш горячих комбинаций фильтров на короткое время снижает нагрузку на базу при пиковом трафике без риска показать сильно устаревшие данные.

**Резюме простыми словами:**
Родитель ставит галочки в фильтрах или разрешает геолокацию — платформа быстро находит подходящие учреждения через индексированные запросы к базе, с честной деградацией, если GPS недоступен.

## Модуль 2. Профиль учреждения

### FR-06: Полная карточка учреждения (контакты, лицензия, программы, ориентиры)

**Цель:** родитель на странице учреждения должен видеть всё нужное для решения «подходит ли нам это место», не переходя на внешние сайты.

**Что нужно реализовать:**
- Поля лицензии, языков обучения, текстового ориентира расположения — сейчас отсутствуют во фронтовой модели, добавляются на схему учреждения как обычные текстовые/массивные колонки.
- Номер лицензии — на старте свободный текст, проверяемый модератором вручную; формальная валидация формата и автоматическая сверка с реестром — дело будущего, по мере готовности такой интеграции.
- Текстовый ориентир — свободный текст, не геокодируется автоматически, это дополнение к точным координатам, не замена.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение указывает номер лицензии, список языков обучения и текстовый ориентир расположения — например «рядом с рынком, вход со двора».

**Реализация в коде:** новые nullable-колонки на сущности учреждения, zero-downtime миграция без дефолтного значения. Backfill не нужен — поля заполняются учреждением при следующем редактировании профиля.

**Резюме простыми словами:** три новых текстовых поля на карточке учреждения, без сложной логики — просто отображаются как есть.

### FR-07: Галерея фото + видеотур

**Что нужно реализовать:**
- Хранение фото — объектное хранилище с раздачей через CDN, не в базе данных. Отдельная таблица галереи с порядком сортировки для перетаскивания в кабинете учреждения.
- Автосжатие фото при загрузке до небольшого целевого размера — на бэкенде через библиотеку обработки изображений или отдельный воркер на очереди, если объём загрузок большой.
- Видеотур — просто ссылка на видео (внешний хостинг или собственный файл), без транскодирования на старте — сложность стриминга видео не оправдана на первом этапе.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение загружает несколько фото через кабинет — каждое автоматически сжимается, сохраняется в хранилище с публичной ссылкой, порядок в галерее задаётся перетаскиванием.

**Реализация в коде:** загрузка через multipart-запрос → воркер сжатия → запись файла в хранилище → запись метаданных в таблицу галереи. Лимит количества фото на профиль — защита от злоупотребления хранилищем.

**Резюме простыми словами:** фото хранятся в облаке, не в базе, автоматически сжимаются, видео — просто ссылка.

### FR-14 / FR-29 / FR-30: Рейтинг по 8 метрикам, порог отзывов, затухание по давности

**Цель:** родитель должен видеть честный, актуальный, устойчивый к манипуляциям рейтинг учреждения — не «средняя оценка за всё время», а взвешенная, защищённая от единичного тролля картина.

**Что нужно реализовать:**
- **8 независимых метрик** (не 9 — более ранняя формулировка с девятой «метрикой» была неточной, девятая величина — просто вычисляемое среднее, не отдельно оцениваемый параметр): качество обучения, условия и помещения, безопасность, питание, развозка, цена/качество, участие родителей, инклюзивность.
- **Нормализованное хранение** оценок по каждой метрике отдельной строкой, а не единым массивом на отзыве — без этого невозможно эффективно считать порог и затухание (нужна агрегация по времени и по метрике одновременно).
- **Порог минимума отзывов:** пока число опубликованных отзывов меньше рекомендуемого минимума (3–5, точное число утверждается отдельно) — карточка показывает статус «Недостаточно отзывов» вместо агрегированной оценки.
- **Затухание веса по давности:** каждой оценке присваивается вес, убывающий экспоненциально со временем — свежие отзывы влияют на среднее сильнее старых. Агрегированный рейтинг по метрике — взвешенное среднее с этими весами, пересчитывается периодически (например раз в сутки) или по запросу с кэшированием на несколько часов.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): у учреждения десятки отзывов за несколько лет. Свежий отзыв с высокой оценкой по безопасности весит заметно больше, чем такой же отзыв многолетней давности — если недавно появилось несколько сообщений об ухудшении, агрегированная метрика отразит это быстрее, чем простое среднее за всё время.

**Реализация в коде:** периодическая фоновая задача пересчитывает агрегированный рейтинг учреждений с изменившимися отзывами — избегает пересчёта на каждый запрос профиля.

**Резюме простыми словами:** 8 отдельных оценок, не 9. Свежие отзывы весят больше старых. Пока отзывов слишком мало — рейтинг не показывается вообще, чтобы один тролль не решал судьбу профиля.

### FR-15 / FR-34: Верификация отзыва через привязку к ребёнку + верификация владельца профиля учреждения

**Цель:** отзыв должен оставлять только реальный родитель реального ребёнка этого учреждения; профиль учреждения должен принадлежать реальному представителю этого учреждения, не самозванцу.

**Что нужно реализовать:**
- Отзыв создаётся только если у пользователя есть запись о привязке ребёнка именно к этому учреждению. Проверка — простая на существование такой записи перед созданием отзыва, в сервисном слое.
- Все статусы привязки (текущий ученик, выпускник, перешёл в другое учреждение) дают право на отзыв — связь была реальной в любом из случаев.
- Верификация владельца профиля — на старте ручная: учреждение прикладывает документ о должности представителя и номер лицензии, модератор проверяет офлайн и вручную выставляет флаг верификации с фиксацией кто и когда проверил. Автоматизация проверки — дело будущего.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): родитель с ребёнком в статусе «выпускник» всё ещё может оставить отзыв — связь была реальной. Пользователь без привязки к этому учреждению вообще не видит кнопку «Написать отзыв».

**Реализация в коде:** перед вставкой отзыва — проверка существования привязки ребёнка к учреждению, при отсутствии — понятный код ошибки (не общий «доступ запрещён», а конкретно «нет привязки»), чтобы фронт мог показать верный текст.

**Резюме простыми словами:** без реального ребёнка в этом учреждении — нельзя оставить отзыв. Без ручной проверки модератором — учреждение не получает галочку верификации.

### FR-16 / FR-17 / FR-35: Модерация отзывов, ответ учреждения, разрешение споров

**Цель:** ни один отзыв не публикуется без проверки; учреждение имеет право ответить публично; спорный отзыв разрешается по прозрачным правилам, а не произвольно.

**Что нужно реализовать:**
- Очередь модерации отзывов со сроком проверки (целевой ориентир — до 24–48 часов), с видимым модератору таймером до просрочки.
- Ответ учреждения на отзыв — публичное поле рядом с самим отзывом.
- Формальный спор: учреждение может эскалировать отзыв, статус меняется на «на рассмотрении». Модератор разрешает по чёткому критерию: отзыв остаётся, если на момент публикации существовала подтверждённая привязка ребёнка к учреждению и нет явных признаков недостоверности; иначе — снимается. Целевой срок разрешения — до 72 часов.
- Каждое решение модератора (одобрение/отклонение отзыва, разрешение спора) фиксируется в журнале действий модерации — кто, когда, что решил и почему.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение оспаривает негативный отзыв, утверждая, что автор никогда не был их клиентом. Модератор проверяет привязку ребёнка автора — если она существует и указывает на это учреждение, отзыв остаётся, решение и обоснование фиксируются в журнале.

**Реализация в коде:** очередь модерации отзывов строится по тому же паттерну «одобрить/отклонить + журнал», что и модерация регистраций учреждений.

**Резюме простыми словами:** отзывы проходят проверку перед публикацией; учреждение может ответить или пожаловаться; решение по жалобе — по чёткому правилу («была ли реальная связь с ребёнком»), не на глаз.

## Модуль 3. Коммуникации

### FR-19: Чат родитель ↔ учреждение

**Цель:** родитель и учреждение общаются напрямую внутри платформы, без телефона/мессенджеров, с сохранённой историей.

**Что нужно реализовать:**
- Постоянное соединение в реальном времени для доставки новых сообщений, с аутентификацией при подключении.
- Хранение истории сообщений — обычная таблица в базе; соединение в реальном времени нужно только для доставки, при повторном заходе история подгружается обычным запросом.
- Доставка во все открытые вкладки/устройства одного пользователя одновременно.
- Индикатор непрочитанных сообщений — считается по количеству новых сообщений после последнего прочтения, обновляется при открытии переписки.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): родитель пишет учреждению вопрос вечером, учреждение онлайн — сообщение доставляется мгновенно. Учреждение офлайн — сообщение остаётся в базе, при следующем входе видно как непрочитанное, плюс приходит уведомление.

**Реализация в коде:** сервер реального времени с одним «хабом» соединений на инстанс сервиса; при нескольких серверах за балансировщиком — рассылка сообщений между инстансами через промежуточный pub/sub-слой, иначе сообщение может не долететь до клиента, подключённого к другому инстансу.

**Резюме простыми словами:** обычный чат с историей в базе, доставка новых сообщений — в реальном времени, работает даже при нескольких серверах.

### FR-20: Уведомления (push, SMS, email)

**Что нужно реализовать:**
- Единый сервис уведомлений, принимающий события от других частей системы (новое сообщение, ответ на отзыв, новость учреждения) и решающий, по какому каналу отправить — по приоритету и настройкам пользователя.
- Push-уведомления в браузере/PWA как основной канал.
- SMS — как запасной канал, когда push недоступен или не доставлен.
- Email — стандартная транзакционная отправка.
- Все каналы отправляются асинхронно через очередь — не блокировать основной запрос ожиданием ответа внешнего провайдера.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение отвечает на отзыв родителя — создаётся уведомление внутри платформы всегда, плюс попытка push-уведомления; если push не доставлен за короткое время — запасной канал SMS.

**Реализация в коде:** очередь сообщений между сервисом-источником события и сервисом уведомлений — развязывает их, позволяет повторить отправку без потери события при сбое внешнего провайдера.

**Резюме простыми словами:** одно событие — платформа сама решает, куда его отправить, с запасным каналом на случай если основной не сработал.

### FR-36 / FR-37: Доска вакансий, отклик, обращение учреждения к соискателю

**Цель:** учреждение публикует вакансию и получает отклики; соискатель публикует резюме и может получить прямое предложение от учреждения, даже не откликаясь сам.

**Что нужно реализовать:**
- Базовое: публикация вакансии учреждением, отклик соискателя — с обязательной идемпотентностью на уровне базы данных, не только проверкой в коде, чтобы защититься от гонки при повторном запросе.
- Публичный список опубликованных резюме, доступный учреждениям без привязки к конкретной вакансии; обращение учреждения к соискателю — тоже идемпотентно (одно обращение на пару учреждение-соискатель).
- Защита от злоупотребления: ограничение на количество обращений от одного учреждения за период — в отличие от отклика (где инициатива у соискателя), здесь инициатива у учреждения, и массовые обращения ко всем подряд ничем не сдерживаются технически без такого ограничения.
- Контакты соискателя скрыты от учреждения до тех пор, пока не начался диалог в переписке — если так настроено самим соискателем.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение просматривает список резюме, видит подходящего кандидата с публичным профилем, отправляет сообщение — соискатель получает уведомление, контакты остаются скрыты, пока он сам не ответит в переписке.

**Реализация в коде:** отдельный эндпоинт обращения учреждения к соискателю, идемпотентность через ограничение уникальности на паре учреждение-соискатель на уровне базы.

**Резюме простыми словами:** вакансии — обычная доска объявлений с откликами. Плюс учреждения могут сами написать понравившемуся соискателю напрямую — с защитой от спама и скрытыми контактами до начала переписки.

## Модуль 4. Аналитика

### FR-22 / FR-23: Дашборд учреждения, экспорт отчётов

**Цель:** учреждение видит, сколько людей смотрит их профиль, откуда приходят, на что кликают — и может выгрузить это в отчёт.

**Что нужно реализовать:**
- Учёт событий просмотра профиля и кликов по ключевым элементам (телефон, сайт, чат) с источником перехода.
- Запись событий — асинхронная, не блокирующая отдачу страницы профиля.
- Агрегация для дашборда через периодические представления (например подневные), а не пересчёт по сырым событиям при каждом заходе учреждения в кабинет.
- Экспорт — выгрузка агрегированных данных за период в CSV; отчёт в PDF — рендер шаблона отдельным процессом.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): учреждение видит на дашборде сводку за неделю — число просмотров профиля, разбивку по источникам перехода, число кликов на кнопку связи.

**Реализация в коде:** отдельная лёгкая таблица событий, не смешивать с основной нагрузкой на данные каталога и отзывов — при росте объёма событий её можно вынести отдельно, не трогая основные данные.

**Резюме простыми словами:** платформа считает просмотры и клики по каждому профилю, показывает учреждению сводку, даёт скачать отчёт.

## Модуль 5. Монетизация и платформа

### FR-25: Тарифы (Free/Pro/Enterprise), продвижение в поиске без влияния на рейтинг

**Цель:** учреждение может платить за более высокую позицию в выдаче поиска — но это никогда не меняет саму оценку рейтинга. Это ключевой тезис доверия платформы («рейтинг нельзя купить»).

**Что нужно реализовать:**
- Поле тарифного плана учреждения — сейчас отсутствует во фронтовой модели вообще.
- Сортировка по умолчанию в поиске (когда пользователь явно не выбрал другую сортировку) учитывает тариф как небольшой буст позиции, не подмену основного критерия — рейтинг как отдельная величина не меняется тарифом ни при каких условиях, буст касается только позиции в списке результатов.
- Управление ценами тарифов и назначение тарифа учреждению — вручную администратором до появления реальной автоматической оплаты; на старте оплата — офлайн, по счёту.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): два учреждения одного района и типа с одинаковым рейтингом — у одного платный тариф. В обычной выдаче поиска платное учреждение показывается выше при прочих равных, но на странице обоих виден одинаковый рейтинг — платный буст не тронул саму оценку.

**Реализация в коде:** буст — простой множитель при сортировке результатов поиска, не отдельный сложный алгоритм ранжирования на первом этапе. Явно фиксировать, что буст не влияет на само поле рейтинга — для доверия и на случай будущего аудита алгоритма.

**Резюме простыми словами:** платный тариф двигает учреждение выше в списке результатов поиска — но никогда не меняет его звёздный рейтинг. Это разные вещи, и это специально гарантируется.

### Модерация регистрации учреждений + журнал действий модерации

**Цель:** ни одно учреждение не появляется в публичном каталоге без проверки; каждое решение модератора прослеживаемо.

**Что нужно реализовать:**
- Регистрация учреждения создаёт запись в статусе ожидания — не видна в публичном поиске до одобрения, фильтрация по статусу должна применяться и на бэкенде, не только на фронте.
- Очередь заявок на модерацию с возможностью одобрить/отклонить.
- Журнал действий модерации — обязательная сущность: при каждом решении (одобрение/отклонение/верификация) фиксируется кто принял решение, что именно, по какой причине и когда.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): модератор отклоняет заявку учреждения без документа о лицензии, указывает причину — запись попадает в журнал, при повторном обращении учреждения видно, кто и почему отклонил в первый раз.

**Реализация в коде:** единый эндпоинт модерации, который в одной транзакции обновляет статус учреждения и пишет запись в журнал — частичная запись (статус изменился, а журнал нет) недопустима.

**Резюме простыми словами:** заявки на регистрацию ждут проверки модератора; каждое решение сохраняется навсегда с причиной — для прозрачности и разбора спорных случаев.

## Модуль 6. Аутентификация и аккаунт

### FR-40: Регистрация, вход, подтверждение почты (обновлено 2026-08-25)

**Цель:** человек создаёт один аккаунт (email+пароль или вход через Google — оба основные пути, телефон опционален), подтверждает владение почтой кодом — и дальше сам решает, дополнять ли профиль, добавлять детей или подавать заявку на регистрацию учреждения.

**Что нужно реализовать:**
- Единая форма регистрации без ветки «кто вы» — учреждение регистрирует не юрлицо, а человек-представитель; выбор роли на входе создал бы два вида аккаунта, что противоречит модели данных (юрлицо — отдельная сущность, привязанная к пользователю, а не тип пользователя).
- **Приоритет каналов (изменено 2026-08-25, было: телефон основной):** email+пароль и вход через Google — оба основные равноправные пути. Телефон — опциональное поле второй очереди, без обязательной SMS-верификации в MVP. Причина изменения: SMS-провайдер в Таджикистане платный за каждую отправку кода, при холодном старте без подтверждённого объёма пользователей это неоправданный расход; email не требует внешнего платного канала.
- Подтверждение почты кодом после регистрации — обязательный шаг перед тем, как аккаунт получает права обычного пользователя. Google-вход подтверждения кодом не требует — владение почтой уже подтверждено провайдером.
- Явное согласие на обработку персональных данных на экране регистрации — обязательный чекбокс, не мелкий текст внизу; факт согласия и версия текста политики сохраняются на сервере как юридическое доказательство (закон РТ №1537).
- После подтверждения — экран выбора дальнейшего действия (дополнить профиль / добавить детей / подать заявку на учреждение), не обязательный шаг, можно пропустить.
- Заявка на регистрацию учреждения переводит роль в реальный статус доступа только после одобрения модератором — не в момент заполнения формы. До одобрения это просто заявка, привязанная к аккаунту заявителя.
- Ограничение частоты запроса кода подтверждения по email и по IP с самого начала — без него повторная отправка кода становится вектором злоупотребления почтовым провайдером.
- Сброс пароля — отдельный поток (запрос кода на почту → новый пароль), для аккаунтов без пароля (чисто Google) недоступен — предлагается привязать пароль отдельно.
- **Право на удаление аккаунта** (закон РТ №1537): пользователь может запросить удаление — сервер выполняет soft-delete с анонимизацией персональных данных (email/телефон/пароль затираются), не мгновенное физическое стирание всех следов — общественно значимые данные (текст отзыва) и журнал модерации сохраняются без привязки к личности.

**Пример** (иллюстративный, конкретные значения могут отличаться в зависимости от ситуации): человек регистрируется по email, подтверждает код, на следующем экране выбирает «подать заявку на учреждение» — заявка уходит в очередь модератора, доступ к панели учреждения появляется только после одобрения. Другой человек входит через Google одним кликом — аккаунт создаётся сразу, шаг подтверждения не нужен.

**Реализация в коде:** хранение пароля — bcrypt/argon2, токены сессии — с ограниченным сроком жизни и ротацией refresh-токена. Подтверждающий код — короткоживущий, с ограничением числа попыток ввода и частоты повторной отправки на один email. Google — обмен id-token на сессию через отдельную таблицу привязки внешней идентичности к аккаунту.

**Резюме простыми словами:** один аккаунт на человека, email или Google — оба одинаково основные способы входа, телефон не обязателен. Право управлять учреждением появляется только после того, как заявку проверит модератор, а не сразу после заполнения формы. Удалить аккаунт можно — данные обезличиваются, а не исчезают бесследно везде.
